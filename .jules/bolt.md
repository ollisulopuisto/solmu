# Bolt's Journal - Critical Learnings Only

## 2026-11-02 - ICU Bidi Property Lookups and Code Point Map Caching
**Learning:** In `src/bidi.rs`, `is_strong_rtl()` is called frequently across characters during galley text layout and rendering. Directly instantiating ICU's `CodePointMapData::<BidiClass>::new()` on each character call introduces high overhead. Furthermore, by Unicode specification, no code point below U+0590 possesses BidiClass `RightToLeft` or `ArabicLetter`. Filtering with `c < '\u{0590}'` allows all ASCII, Latin, Greek, and Cyrillic characters to exit immediately without any ICU lookup, and caching `CodePointMapDataBorrowed::<BidiClass>` via `OnceLock` eliminates repeated table instantiation for RTL code points.
**Action:** Use script/block boundaries (such as `c < '\u{0590}'` for RTL) to fast-path Unicode character classification, and cache ICU borrowed code point maps in a static `OnceLock` across the application lifecycle.

## 2025-05-18 - Full Cargo Test Suite Timeout & Search Key Optimization
**Learning:** Running `cargo test` without filters or compiling full release benchmarks takes a very long time and can hit timeout limits because of the massive workspace dependency graph (e.g. `waproto`, `whatsapp-rust`, audio libraries). In `src/util.rs`, `search_key()` performs accent-stripping search key normalization using `icu_properties::CodePointMapData::<GeneralCategory>::new()`. Calling `new()` repeatedly inside the iterator filter closure creates the code point map lookup data repeatedly per non-ASCII character, instead of instantiating it once outside the closure or iterator chain.
**Action:** Always filter tests specifically (e.g., `cargo test --lib -- util`), and hoist ICU lookup map instantiation outside per-character closures in character processing loops.

## 2026-11-07 - Token-hashing allocations on every solmu-reader request
**Learning:** `hash_token` ran 32 per-byte `format!("{byte:02x}")` allocations and `Registry::authenticate` re-lowercased every stored hash (`to_ascii_lowercase()`) on every authenticated solmu-reader request (rate-limit key + authenticate). Replacing the hex encode with a stack-buffer lookup table and making `ct_eq` case-insensitive (constant-time, no per-entry allocation) cut per-request cost ~2–3x in debug profile (authenticate 100 clients 139µs→69µs; hash_token 3µs→1µs). Output is identical (benchmark checksums unchanged) and all 16 `read_api` tests pass. This is orthogonal to the registry mtime cache (PR #216), which does not touch per-request hashing.
**Action:** Hoist per-byte `format!` out of hot loops into stack-buffer lookup tables; avoid per-iteration `String` allocations in constant-time scans; measure auth paths in isolation since registry caching and token hashing are independent costs.

## 2026-11-07 - solmu-reader client registry cache
**Learning:** mtime alone is not safe for authorization caching. chmod leaves mtime unchanged; atomic replacements can preserve it. Unix cache hits now check private mode and device/inode/ctime/mtime/length. Other platforms reload rather than infer unchanged authority. Immutable Arc snapshots release the cache mutex before upstream work; otherwise one slow request serializes the server.
**Action:** Keep auth safety and concurrency regressions at the HTTP boundary, and update every Shared initializer. Benchmark claims from the original optimization are not revalidated after the safety repair.

## 2026-11-08 - Participant list and names sort key allocations
**Learning:** In `App::participant_list` and `App::participant_names`, sorting participant lists using `sort_by_key` computed `.to_lowercase()` across $O(n \log n)$ comparisons, and adjacent duplicate counting in `participant_names` recomputed `.to_lowercase()` on every peek. Precomputing `(sort_key, item)` once per participant reduced lowercasing allocations from $O(n \log n)$ to $O(n)$ and sped up participant list sorting by ~2.1x (372µs -> 176µs for 100 participants) while preserving exact sort stability and duplicate counting.
**Action:** In collection sorting and subsequent runs over sorted elements (like grouping / deduplication), pair items with precomputed lowercase keys `(key, item)` to avoid redundant reallocations in both the sort comparison closure and subsequent scan steps.

## 2026-11-09 - Phone number intermediate allocation and string pre-allocation
**Learning:** `phone()` is called repeatedly per-chat and per-contact during UI rendering and list filtering. The function previously filtered digits into a newly allocated `String` on every call (`digits.chars().filter(...).collect()`). For the vast majority of calls where inputs are already raw ASCII digits (from JIDs, normalized contacts, or protocol payloads), borrowing `Cow<'_, str>` via `digits.bytes().all(|b| b.is_ascii_digit())` eliminates the intermediate heap allocation entirely. Furthermore, estimating and pre-allocating capacity for the formatted string and direct prefix-checking in `french_phone` reduced `phone()` latency by ~37% (from ~1650 ns down to ~1040 ns per call in debug builds).
**Action:** In string formatting helpers that take potentially clean inputs, use `Cow<'_, str>` with a fast byte scan to borrow unmodified slices instead of always allocating intermediate filtered strings.

## 2026-11-11 - Zero-allocation ASCII matching and short-circuiting in merged search
**Learning:** `search_matches` in `src/merged.rs` runs on every loaded message during linked chat search in `src/ui/merged.rs`. It previously called `.to_lowercase()` on `query.trim()` regardless of whether the query was empty, and allocated lowercase `String`s for `[body, network, sender]` unconditionally. Fast-returning `true` on empty queries, short-circuiting across candidates sequentially, and using a sliding window byte scan with `eq_ignore_ascii_case` when `query.is_ascii()` eliminates all heap allocations for ASCII queries (the common case) and reduced search matching latency by 44.6% (from 92.4 ms down to 51.1 ms per 500k calls, a 1.81x speedup).
**Action:** For string search over multiple text attributes, check for empty trimmed query first, short-circuit sequentially to avoid evaluating subsequent fields once a match is found, and use zero-allocation byte window scanning for ASCII queries instead of calling `.to_lowercase()`.
